# Phase 1 — UI Design Contract

> Visual and interaction contract for the calm, compact trust-and-status surfaces required by Phase 1. Generated by gsd-ui-researcher for verification by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn, already initialized in `frontend/components.json` |
| Preset | New York style, neutral base, CSS variables, no class prefix |
| Component library | shadcn wrappers over Radix UI; preserve existing checked-in components |
| Icon library | Lucide React |
| Font | Source Sans 3 via `--font-source-sans-3` |

The existing desktop shell, sidebar, settings tabs, fixed-bottom recording controls, Radix dialogs, Sonner toasts, and meeting-detail split view remain the structural baseline. Phase 1 adds trust and status information to those surfaces; it does not redesign navigation or introduce a second visual system.

The Telu palette in `docs/telu/color-palette.md` supersedes the current grayscale/blue defaults for new or touched Phase 1 surfaces. Executor work must map the CSS variables in `globals.css` to the Telu values instead of scattering new literal colors through components.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, dense metadata |
| sm | 8px | Status-chip padding, inline action gaps |
| md | 16px | Default control and alert spacing |
| lg | 24px | Dialog and settings-section padding |
| xl | 32px | Page gutters and major panel gaps |
| 2xl | 48px | Separation between unrelated settings groups |
| 3xl | 64px | Page-level breathing room only |

Exceptions: icon-only controls and row hit areas have a 44px minimum target; 1px borders and 2px focus rings are visual strokes, not layout spacing tokens.

Dense telemetry values use 4px vertical gaps inside the Diagnostics detail view only. Normal recording and meeting-history surfaces never adopt diagnostic density.

## Typography

Use exactly three sizes and two weights across new Phase 1 UI. Source Sans 3 remains the only interface font.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Metadata | 12px | 400 | 1.4 |
| Body | 14px | 400 | 1.5 |
| Label / action | 14px | 600 | 1.4 |
| Section heading | 24px | 600 | 1.2 |

Use tabular numerals for duration, queue depth, oldest age, timestamps, and resource measurements. Meeting titles and provider destinations use normal proportional text. Do not use all caps for statuses; use sentence case such as `Recovered with gaps`.

Long IDs are technical details: render them at 12px, allow selection/copy, and keep them out of normal recording controls and meeting-list rows.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Warm Off-white `#F7F7F4` | Application background and diagnostics canvas |
| Secondary (30%) | White `#FFFFFF` | Cards, sidebar, dialogs, fixed status surfaces |
| Accent (10%) | Telu Indigo `#6366E8` | Primary non-recording CTA, selected state, links, focus rings, active Settings tab |
| Primary text | Ink `#17191F` | Headings, body text, strong icons |
| Supporting text | Slate `#727783` | Metadata, helper text, secondary labels |
| Border | Soft Grey `#E6E6E2` | Dividers, outlines, quiet structure |
| Destructive / attention | Soft Coral `#FF6B62` | Active recording, destructive actions, provider failure, incomplete or missing data |

Accent reserved for: primary non-recording actions, selected navigation or list row, text links, focus indicators, and the active Settings tab underline.

Fresh Mint `#67E8C5` is not used in Phase 1. It remains reserved for future evidence-backed live-assistance moments. Local, LAN, and Remote are not success/error judgments and therefore use neutral white/Ink/Soft Grey chips differentiated by icon and text, not green/red fills. Complete, incomplete, recovered, and unavailable states always include visible words and icons; color is supplementary.

Soft Coral remains the recording color even though it is also the attention color. Do not use coral for ordinary remote-provider labels or generic emphasis.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Start recording` |
| Empty state heading | `No diagnostic runs yet` |
| Empty state body | `Run a baseline scenario, then return here to inspect its local results.` |
| Error state | `Telu couldn’t reach {destination}. {provider} is still selected, and no data was sent to another provider.` Actions: `Retry`, `Change provider`, `Cancel` |
| Destructive confirmation | `Delete interrupted meeting`: `Delete “{meeting title}”? Its local recovery data will be removed. This cannot be undone.` Actions: `Keep meeting`, `Delete meeting` |

### Required phase copy

| Surface / state | Exact pattern |
|-----------------|---------------|
| Local route | `{Capability}: Local · This device` or `{Capability}: Local · {loopback origin}` |
| LAN route | `{Capability}: LAN · {scheme}://{host}:{port}` |
| Remote route | `{Capability}: Remote · {scheme}://{host}` |
| Unencrypted LAN route | Append `Not encrypted` after the HTTP destination; do not hide the scheme |
| Finalizing, queued work | `Finalizing recording` and `{depth} {item/items} remaining · oldest waiting {age}` |
| Finalizing, no queued work | `Finalizing recording` and `No transcript work pending · saving meeting` |
| Complete status | `Complete` |
| Incomplete status | `Incomplete · {gap count} {gap/gaps}` |
| Recovered status | `Recovered with gaps · {gap count} {gap/gaps}` |
| Legacy status | `Completion not verified` |
| Incomplete detail | `Some audio or transcript content is missing. Review the recorded gaps before relying on this meeting.` |
| Recovered detail | `Recovery preserved the available content, but some audio or transcript content is still missing.` |
| Recovery success without gaps | `Meeting recovered. No recorded gaps remain.` |
| Recovery result with gaps | `Meeting recovered with {gap count} {gap/gaps}.` |
| Diagnostics privacy note | `Diagnostic data stays on this device unless you export a local copy.` |
| Export review title | `Review diagnostic export` |
| Export review body | `Transcript text and audio are excluded unless you include them below.` |
| Export action | `Export local copy` |

Copy rules:

- Use `Telu`, not `Meetily`, in all new Phase 1 copy.
- Name the capability (`Transcription` or `Summary`), the boundary (`Local`, `LAN`, or `Remote`), and the concrete destination. A provider brand alone is insufficient.
- Never say `complete`, `saved`, or `recovered successfully` until the Rust-owned lifecycle result permits that claim.
- Do not use celebratory punctuation for recovery or completion. These are factual states.
- Provider errors state what failed, what was preserved, and the next actions. A toast may announce the error, but the actionable alert remains in the originating surface until resolved or cancelled.
- Use singular/plural grammar for items, gaps, runs, and meetings.

## Interaction Contracts

### Provider boundary disclosure

1. The Rust-resolved route is the displayed source of truth. React never infers Local/LAN/Remote from provider name.
2. The route appears in provider settings immediately after selection and again at the action boundary before data-bearing work begins.
3. The compact row order is: capability label, location chip, destination. Examples: `Transcription  [Local]  This device · Parakeet`; `Summary  [Remote]  https://api.openai.com`.
4. Destination text displays the origin only: scheme, host, and non-default port. Strip credentials, tokens, query strings, and sensitive path segments. Local built-in engines display `This device` plus the engine/model name.
5. A destination longer than the available width truncates in the compact row with a middle ellipsis; keyboard focus or click opens a non-tooltip detail row containing the selectable full sanitized origin.
6. LAN and Remote routes require no repetitive confirmation modal when the unchanged disclosure is already visible at the action. A newly selected route or route-class change must be visible before the CTA becomes enabled.
7. If runtime resolution differs materially from the displayed contract, block the operation and use the unavailable-provider alert. Preserve the selected provider and all local data. Never present or perform a fallback choice.

### Unavailable provider

1. Render an inline destructive Alert at the point of action with title `{Capability} provider unavailable` and the required error copy.
2. Present actions in this order: `Retry` (primary), `Change provider` (outline), `Cancel` (ghost). `Change provider` focuses the existing provider control; `Cancel` closes only the attempted operation.
3. Disable the data-bearing CTA while retry is in flight and label it `Retrying…`; do not mutate the selected provider.
4. During an active meeting, the alert must separately state the authoritative capture outcome. Use `Recording continues locally` only when Rust confirms capture is still durable; otherwise state `Recording stopped` and surface the resulting incomplete state.
5. Error detail may expose a redacted technical code under `Show technical details`; the default alert does not show stack traces or raw payloads.

### Recording finalization

1. Clicking Stop immediately disables pause/stop controls, ends the coral recording pulse, and swaps the fixed-bottom control card for the finalization card in the same location. Do not blank the main transcript.
2. The card shows a 16px activity indicator, `Finalizing recording`, and the real `{depth} items remaining · oldest waiting {age}` line from Rust. Format age as `<1s`, `12s`, or `2m 04s`.
3. Update visible values whenever the authoritative snapshot changes. Use `aria-live="polite"` for lifecycle text; throttle spoken queue updates so screen readers are not notified more than once every five seconds.
4. Do not render a progress bar or percentage unless the backend provides a true finite total. Queue depth may rise only if the authoritative ledger permits it; the UI never smooths, predicts, or clamps the value.
5. When depth is zero but a durable write remains, show the required no-pending-work copy. `Complete` appears only after capture is closed, all accepted work is terminal, and durable writes succeed.
6. On deadline or failure, replace the card with `Meeting saved as incomplete`, a one-sentence reason, and actions `View meeting` and `Review gaps`. Do not auto-dismiss this result; keep it until the user acts or deliberately closes it.
7. A new recording may start only after the prior meeting has reached a durable terminal lifecycle. The previous meeting identity is never reused.

### Completeness and history

1. Every Phase 1 meeting exposes one visible label: `Complete`, `Incomplete`, `Recovered with gaps`, or `Completion not verified` for migrated legacy records lacking evidence. Never backfill legacy rows as complete based on silence.
2. In meeting-history rows, put the status beneath the title as 12px metadata so it remains visible when row actions are hidden. The meeting title wraps to two lines, then truncates; the status never truncates.
3. In meeting detail, show the status beside the title. Complete meetings need no banner. Incomplete, recovered-with-gaps, and legacy-unverified meetings show a persistent Alert above transcript content.
4. `Review gaps` opens a list ordered by recording-relative time. Each row includes gap type, microphone/system-audio source when known, time range, and plain-language reason. Unknown values display `Unknown`; they are never omitted.
5. Zero gaps after reconciliation changes the outcome to recovered without gaps only when Rust confirms the gap ledger and accepted work are fully reconciled. UI state alone cannot promote completeness.

### Recovery

1. Keep the existing two-pane recovery dialog: candidate meetings on the left, preview and completeness detail on the right. The canonical meeting ID remains stable but is not shown by default.
2. The candidate row shows meeting title, last activity, available final-segment count, audio availability, and current completeness label. Never describe provisional text as durable transcript evidence.
3. `Recover meeting` is the primary action. While reconciliation runs, disable selection and delete controls and show `Recovering meeting…` without optimistic success copy.
4. After reconciliation, do not automatically close or navigate. Replace the preview footer with the authoritative result and actions `View meeting` and `Done`. If gaps remain, use the required recovered-with-gaps copy and expose `Review gaps`.
5. Repeating recovery for the same meeting displays the same canonical meeting and updated reconciliation result. It never adds a duplicate candidate row.
6. `Delete meeting` retains a destructive confirmation. Closing the dialog or choosing `Keep meeting` preserves the recovery record.

### Diagnostics and local export

1. Add `Diagnostics` as the final Settings tab. Normal recording surfaces show only the provider route, lifecycle, queue depth, and oldest age needed for trust; CPU, memory, counters, run IDs, and raw stage timing stay here.
2. The default tab view contains the privacy note and recent-run list. Each run row shows scenario, start time, result (`Pass`, `Fail`, or `Unknown`), effective route, duration, and a `View details` action.
3. Run details group information in this order: Result and limitations; environment; stage timing; queue and terminal outcomes; resources; provider route and outbound attempts; redacted errors. Preserve outliers and unknown values.
4. Technical tables scroll within their panel. Freeze the first column where practical, use tabular numerals, and allow IDs to be copied. Do not graph a metric when a compact value/distribution table is clearer.
5. `Export diagnostics` opens `Review diagnostic export`. List included categories, destination folder, and redaction policy. Transcript text and audio switches are off by default and require separate explicit changes each export.
6. Export creates a sanitized local copy. It does not upload or share. Success copy is `Diagnostic copy exported locally`; include `Show in folder`. Failure copy states the filesystem reason and offers `Try again` or `Choose another folder`.

## Layout and Responsive Behavior

- Preserve the existing fixed 256px expanded sidebar and 64px collapsed sidebar. New status metadata must fit without widening either state.
- Settings content remains centered at a maximum width of 1152px with 32px page gutters. The Diagnostics run list and detail occupy one column; do not add a dashboard grid.
- At window widths below 900px, route rows wrap destination text below the capability/chip line, recovery becomes a vertically stacked candidate list and preview, and dialog gutters reduce to 16px.
- Fixed-bottom recording/finalization cards use `max-width: 750px`, remain centered in the content area, and reserve 16px from the window edge. They must not overlap the sidebar or status dialogs.
- Long meeting titles wrap to two lines. Provider origins and error messages wrap in detail views; compact route rows use middle truncation with a full sanitized value available on activation.
- Lists use contained vertical scrolling. Avoid page-level horizontal scrolling; technical tables alone may scroll horizontally inside their panel.

## Accessibility and Motion

- All icon-only actions have a visible-on-focus accessible name and a 44px hit target. Tooltips supplement names; they never carry required privacy or status information.
- Focus rings are 2px Telu Indigo with a visible offset on white and Warm Off-white surfaces.
- Provider failures use `role="alert"`. Finalization and recovery progress use `role="status"` with polite announcements. Destructive confirmations trap focus through the existing Radix Dialog behavior.
- Status chips pair Lucide icon and text: Laptop/`Local`, Network/`LAN`, Cloud/`Remote`, CheckCircle/`Complete`, AlertTriangle/`Incomplete`, RotateCcw/`Recovered with gaps`, CircleHelp/`Completion not verified`.
- The existing recording pulse may continue for active recording. Under `prefers-reduced-motion`, use a static Soft Coral dot. Finalization uses opacity-only entrance up to 200ms; no bouncing, vibrating, or decorative telemetry animation.
- Never rely on coral, indigo, or icon shape alone. The visible state word is mandatory.
- Keyboard order follows the visible layout. `Retry`, `Change provider`, and `Cancel` are reachable without entering technical details.
